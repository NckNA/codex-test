# Архитектура и карта клинических сценариев (Clinical Domain Map)

> [!TIP] Одобренная архитектура
> Эта версия плана составлена с учётом экспертной медицинской экспертизы. Мы полностью разделяем физическое состояние зуба, его диагнозы, работы и визуализацию на схеме.

## 1. Новая модель данных (Data Schema)

Для того чтобы избежать "супа из данных", интерфейс и база данных будут опираться на строгую типизацию. Текущий объект `ToothRecord` будет радикально переработан:

```typescript
export type ToothPresenceStatus = 
  | 'natural'          // естественный зуб
  | 'missing'          // отсутствует давно / зона дефекта
  | 'extracted_recent' // недавно удалён / лунка
  | 'implant'          // установлен имплант
  | 'root_remnant'     // остаток корня
  | 'unerupted'        // непрорезавшийся зуб
  | 'impacted'         // ретинированный / дистопированный
  | 'primary'          // молочный зуб
  | 'supernumerary';   // сверхкомплектный зуб

// То, как зуб ВЫГЛЯДИТ на формуле (отдельно от диагнозов)
export type VisualState = 'healthy' | 'caries' | 'pulpitis' | 'periodontitis' | 'implant' | 'missing' | 'crown' | 'filled' | 'root';

export interface ToothRecord {
  toothId: string;              // 11, 12, 55, 64 и т.д.
  dentition: 'permanent' | 'primary';
  presenceStatus: ToothPresenceStatus;

  visualState?: VisualState;    // Цвет/иконка на зубной карте (UI only)
  
  // Клинические списки
  diagnoses: string[];          // Ссылки на справочник (кариес, периодонтит...)
  plannedWorks: string[];       // Ссылки на работы (установка импланта...)
  completedWorks: string[];     

  // Детальные зоны (на будущее)
  surfaces?: string[];          // O, M, D, V/B, L/P, Incisal
  perio?: Record<string, any>;
  endo?: Record<string, any>;
  implant?: Record<string, any>;
  prosthetic?: Record<string, any>;
  bone?: Record<string, any>;
}
```

## 2. Конфиг-управляемый UI (Config-driven UI)

Вкладки в окне `ToothEditorModal` больше не будут "захардкожены". Мы создадим файл `src/config/clinicalDictionaries.ts`, который будет управлять отображением.

**Пример логики UI по статусам:**

*   **`natural`**: Вкладки: *Коронка (поверхности) / Пульпа (каналы) / Корень (периапикальная зона) / Пародонт (десна) / Кость / Ортопедия / Окклюзия*.
*   **`implant`**: Вкладки: *Супраструктура / Тело импланта / Десна / Кость / Обслуживание*.
*   **`missing`**: Вкладки: *Кость / Десна / Планирование*.
*   **`extracted_recent`**: Вкладки: *Лунка / Хирургия*.
*   **`primary`**: Вкладки: *Молочная коронка / Молочные каналы / Смена зубов*.

## 3. План реализации (Шаги к разработке)

1. **Создание словарей (Config):** Написание файла `clinicalDictionaries.ts` со всеми диагнозами и настройками отображения вкладок (основано на файле `clinical_lists.md`).
2. **Обновление Типов (`types/index.ts`):** Внедрение новой структуры `ToothRecord`, миграция старого свойства `condition` в `visualState` и добавление массивов `diagnoses` и `plannedWorks`.
3. **Рефакторинг `ToothGrid.tsx`:** Перевод отрисовки SVG с использования старого `condition` на использование нового `visualState` и `presenceStatus`.
4. **Обновление Редактора (`ToothEditorModal.tsx`):** 
   - Замена старого селектора состояния на переключатель `presenceStatus`.
   - Динамический рендер вкладок на основе `presenceStatus`.
   - Рендер диагнозов и работ из Конфига в зависимости от активной вкладки.
   - Раздельный выбор диагнозов и отдельная кнопка для "Цвета на формуле (`visualState`)".
## 4. Архитектура управления справочниками (Dictionary Management)

Как вы верно заметили, справочники не должны быть жестко зашиты в коде, они должны управляться из "Врачебной части" (Настройки клиники) и связываться с пациентом.

### Схема потоков данных:
1. **База данных (Supabase):** 
   - Таблица `clinical_dictionary_diagnoses` (ID, Название, Категория/Вкладка, Статус присутствия).
   - Таблица `clinical_dictionary_works` (ID, Название, Категория/Вкладка, Статус присутствия, Цена, Валюта).
2. **Врачебная часть (Админка):** 
   - Маршрут `/settings/clinical-dictionaries`. Интерфейс, где Главврач может добавлять новые работы и диагнозы, привязывая их к конкретным вкладкам (например, добавить "Новая костная пластика" во вкладку "Кость" для "Отсутствующего зуба").
3. **Глобальный State (React Context / Store):** 
   - Приложение на старте (или лениво при входе в зубную карту) загружает эти справочники в `useClinicalDictionaries()`.
4. **Окно редактирования зуба (Patient UI):**
   - Выпадающие списки `SuggestionInput` больше не берут хардкод. Они запрашивают данные из стора: `getWorksByPresenceAndTab(activePresence, activeTab)`.

### План реализации (Шаги к разработке)

1. **Создание интерфейсов (Config & Types):** Создадим базовые типы словарей и начальный JSON-конфиг (Seed) на основе `clinical_lists.md`, чтобы UI мог работать сразу, пока база данных не подключена к админке.
2. **Обновление Типов (`types/index.ts`):** Внедрение новой структуры `ToothRecord`, миграция `condition` в `visualState` и добавление `diagnoses` / `plannedWorks`.
3. **Рефакторинг `ToothGrid.tsx`:** Перевод отрисовки SVG на использование `visualState`.
4. **Обновление Редактора (`ToothEditorModal.tsx`):** 
   - Замена старого селектора состояния на переключатель `presenceStatus`.
   - Динамический рендер вкладок на основе `presenceStatus`.
   - Рендер диагнозов и работ из Конфига/Стора в зависимости от активной вкладки.
5. **Создание Админ-маршрута:** Заготовка страницы "Справочники" во Врачебной части для будущего CRUD управления.
