# RECON-DOCTOR-REAL-001: Plan doctor data source alignment

## Summary
This document analyzes how to align the doctor data source with Supabase to unblock the migration of `AppointmentRepository`. The core issue is that the current UI uses static, non-UUID string IDs (`d1`, `d2`) from `localStorage`, which are incompatible with the Postgres `appointments.doctor_id` UUID Foreign Key. The safest and most scalable solution is to implement a read-only `SupabaseDoctorRepository` and seed initial doctor data directly into Postgres, keeping the legacy dev fallback intact.

## Files Inspected
- `src/data/repositories/DoctorRepository.ts`
- `src/data/hooks/useClinicDoctors.ts`
- `src/data/seed.ts`
- `src/utils/storage.ts`
- `src/types/index.ts`
- `supabase/migrations/0001_initial_schema.sql`
- `supabase/seed.sql`

## 1. Current DoctorRepository Shape
- **Interface**: `listDoctors()`, `listActiveDoctors()`.
- **Nature**: Read-only from the frontend perspective (no `createDoctor` or `updateDoctor` methods exist).
- **Backend**: `LocalStorageDoctorRepository` which directly calls `storage.getDoctors()`.
- **Usage**: Used by `useClinicDoctors.ts`, which drives the columns and filters on the Schedule/Calendar pages.
- **Tenant Scope**: Globally seeded in `localStorage`, meaning no local tenant separation exists.

## 2. Current Doctor Data
- **Demo Doctors**: Seeded via `src/data/seed.ts` (`demoDoctors`).
- **IDs**: Hardcoded short strings (`d1`, `d2`, `d3`).
- **Fields**: `id`, `fullName`, `specialization`, `cabinet`, `color`, `active`.

## 3. Supabase Schema Fit
The `doctors` table in Postgres perfectly accommodates the frontend needs:
- `id`: `uuid`
- `tenant_id`: `uuid` (required)
- `user_id`: `uuid` (optional, can be null for now)
- `full_name`: `text` (maps to `fullName`)
- `specialization`, `cabinet`, `color`: `text`
- `active`: `boolean`
- **RLS**: Policies are already in place isolating doctors by `tenant_id`.

## 4. Appointment Dependency / Blocker
If we migrated `AppointmentRepository` today:
- The UI's `useScheduleAppointments` hook would attempt to create an appointment.
- The payload would contain a `doctorId` from the UI, e.g., `'d1'`.
- Postgres would immediately throw a type error (`invalid input syntax for type uuid`) or a Foreign Key constraint error because `appointments.doctor_id` must be a valid UUID present in `doctors(tenant_id, id)`.
- Without UUID-based doctors, Supabase appointments cannot be created.

## 5. Possible Strategies

**Option A: Migrate DoctorRepository to Supabase first (RECOMMENDED)**
- Implement `SupabaseDoctorRepository` with `listDoctors` and `listActiveDoctors`.
- Create a factory `createDoctorRepository({ backend, tenantId })`.
- Seed 4-5 doctors with valid UUIDs into `supabase/seed.sql` for the `Demo Clinic A` tenant.
- **Why it's best**: Fully cleanly separates concerns. Supabase UI gets UUID doctors, which will cleanly insert into Supabase appointments later. Dev mode stays untouched, so legacy `localStorage` appointments (which use `d1`, `d2`) do not break.

**Option B: Seed doctors in Postgres, keep UI local**
- **Fatal flaw**: The local UI would still pass `d1` to the Supabase `AppointmentRepository`, failing the UUID cast.

**Option C: Hardcode UUIDs in local `demoDoctors`**
- Change `src/data/seed.ts` to use fixed UUIDs matching `seed.sql`.
- **Risk**: This breaks any existing local appointments in developers' browsers that currently reference `d1`. It also blurs the line between the `dev` legacy sandbox and the Supabase environment.

## 6. ID Strategy
- **Supabase Mode**: Doctor IDs will be real UUIDs generated by Postgres during the seed.
- **Dev Mode**: Doctor IDs remain `d1`, `d2` to preserve legacy local state safely.
- No frontend UUID generation for doctors is needed yet since there is no "Add Doctor" UI.

## 7. Tenant/RLS Readiness
- The `doctors` table requires a `tenant_id`.
- `TenantContext` properly provides this.
- Unauthenticated / no-tenant users are safely blocked by the UI gate before reaching the schedule.

## 8. Query Design
- `listDoctors()`: `supabase.from('doctors').select('*').eq('tenant_id', tenantId)`
- `listActiveDoctors()`: `supabase.from('doctors').select('*').eq('tenant_id', tenantId).eq('active', true)`

## 9. Tests Required Before Implementation
- Factory tests ensuring `dev` mode returns `LocalStorageDoctorRepository`.
- Mapping tests for `SupabaseDoctorRepository` (e.g., `full_name` -> `fullName`).
- `useClinicDoctors.test.tsx` hook test.

## 10. Browser QA Plan
- Run app in `supabase-active` mode.
- Log in.
- Open Schedule page.
- Verify doctor columns render properly with the new Postgres-seeded doctors.
- Check React DevTools or Network tab to verify the doctor IDs are valid UUIDs.
- Verify Dev fallback mode still successfully renders `d1`/`d2` columns.

## 11. Risks and Blockers
- **Empty Schedule for New Tenants**: Because there is no UI to add new doctors, a user creating a brand-new Clinic in Supabase will have 0 doctors and an empty schedule. This is acceptable for the current migration scope, but is a known product limitation.
- **Dependency Chain**: We must merge the Doctor migration and seed changes **before** we can implement `AppointmentRepository`.
