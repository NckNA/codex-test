# AUDIT-001 Repository Structure Inventory Report

## Task ID
AUDIT-001

## Summary
This read-only audit inspected the current physical structure of the DentalFlow CRM repository to document its folders, entry points, configuration files, and existing prototype/skeleton boundaries. No application code, settings, or documentation rules were changed during this task.

## Repository root overview
Top-level folders and key files include:
- `.git/` - Version control.
- `_ai_work/` - Documentation, architecture rules, and AI agent reports.
- `backend/` - Directory for the backend/API proxy skeleton.
- `dist/` - Build output directory (generated by Vite).
- `node_modules/` - Frontend dependencies.
- `public/` - Static public assets.
- `src/` - Frontend source code (React).
- `package.json` & `package-lock.json` - Frontend package definitions.
- `vite.config.ts` - Vite configuration.
- `tsconfig.*.json` - TypeScript configurations.
- `eslint.config.js` - ESLint configuration.
- `README.md` - Standard project readme.

## Frontend structure
The `src/` directory contains:
- `assets/` - Images and SVGs (e.g., `hero.png`, `react.svg`).
- `components/` - Subdivided by domain: `common`, `dental`, `layout`, `patients`, `schedule`, `treatment`.
- `context/` - React context providers (e.g., `ScheduleContext.tsx`).
- `data/` - Hardcoded data files (e.g., `seed.ts`).
- `hooks/` - Custom React hooks (e.g., `useScheduleContext.ts`).
- `integrations/` - Contains amoCRM types and mappers (`amocrm/amoCrmMapper.ts`).
- `pages/` - Dedicated page components for routing (e.g., `PatientCardPage.tsx`, `CrmPage.tsx`, `SchedulePage.tsx`, etc.).
- `types/` - TypeScript interface definitions (`index.ts`).
- `utils/` - Utility functions, prominently `storage.ts` which manages `localStorage`.
- `index.css` & `main.tsx` - Styling entry and application entry point.

## Backend structure
The `backend/` directory acts as a proxy skeleton:
- `package.json` - Identifies the project as `dentalflow-integration-proxy`.
- `src/server.js` - Primary entry point.
- `src/config.js` - Configuration loader.
- `src/routes/` - Express routes (`healthRoutes.js`, `amoCrmRoutes.js`).
- `src/services/` - Integration logic (`amoCrmClient.js`, `amoCrmStateStore.js`, `amoCrmTokenStore.js`).
- `src/utils/` - Helpers (`jsonResponse.js`).
- `.env.example` - Example environment variables.

## _ai_work structure
The `_ai_work/` directory houses the project's memory and rules:
- `SOURCES/` - Contains the foundational architectural documents 00 through 18, plus `SOURCES_INDEX.md`.
- `REPORTS/` - Contains Markdown reports for every completed AI task.
- `TASKS/` - Contains task templates.
- Legacy or root-level rules: `AI_WORKFLOW.md`, `ARCHITECTURE_CURRENT.md`, `MEDICAL_DOMAIN_RULES.md`, `PRODUCT_CONTEXT.md`, `RISKS.md`, `STORAGE_RULES.md`, `UI_RULES.md` and amoCRM integration docs.

## Prototype/skeleton indicators
Evidence of the system's current prototype state based strictly on files:
- **`localStorage` dependence:** `src/utils/storage.ts` and `src/data/seed.ts` strongly indicate the frontend relies on browser storage rather than a true database backend.
- **Backend status:** The `backend/` directory is isolated and primarily named/structured around amoCRM proxying (`dentalflow-integration-proxy`), implying it doesn't currently serve the core CRM data (patients, appointments).
- **amoCRM status:** `backend/src/services/amoCrmTokenStore.js` and `backend/src/routes/amoCrmRoutes.js` exist, suggesting an OAuth skeleton is present. `src/integrations/amocrm/amoCrmMapper.ts` in the frontend indicates DTO mapping logic is partially on the client side.

## Risk areas for next audits
Based on the file structure, the following areas require deep auditing:
- **`src/pages/` and `src/components/`:** To ensure components are not overly coupled (e.g., checking boundaries of `PatientCardPage.tsx` and `DentalChartTab.tsx`).
- **`src/utils/storage.ts`:** To audit the exact shape of `localStorage` data before planning a database migration.
- **`src/integrations/amocrm/amoCrmMapper.ts`:** To verify if the frontend is inappropriately handling medical data filtering or making direct calls.
- **`backend/`:** To audit how robust the proxy skeleton actually is, and if it enforces any tenant isolation or security measures yet.
