# RECON-APPOINTMENT-REAL-001: Plan AppointmentRepository Supabase migration

## Summary
This document analyzes the readiness and strategy for migrating `AppointmentRepository` from `localStorage` to Supabase. The analysis confirms that while the Supabase schema (`appointments` table) is an excellent fit for our domain, **a critical blocker exists regarding the `doctors` relationship.** Since doctors are currently sourced from `localStorage` with non-UUID string IDs (e.g., `d1`, `d2`) and are not seeded in the local Supabase environment, migrating appointments now would trigger Foreign Key and UUID type violations. Therefore, the migration of `AppointmentRepository` must be deferred until the doctor data source is aligned.

## 1. Current AppointmentRepository Shape
- **Interface**: Exposes `listAppointmentsByPatient`, `listAppointments`, `createAppointment`, `updateAppointment`, `deleteAppointment`.
- **Backend**: Direct synchronous reads/writes to `localStorage` via `storage.ts`.
- **Usage**: Used by `useScheduleAppointments.ts` (and indirectly by patient profile views if hooked).
- **Filtering/Sorting**: Handled partially in the repository (`listAppointmentsByPatient` filters and sorts) and partially in UI components.
- **IDs**: Generated by the frontend (likely using prefixes like `a{Date.now()}`), stored as strings.
- **Data Model**: Appointments are tied to `doctorId` (required by UI), `patientId` (optional for blocked slots), `cabinet`, and `start`/`end` times (as ISO strings).

## 2. Supabase Schema Fit
The `appointments` table in Postgres aligns well with the frontend `Appointment` type:
- `id`: `uuid` (requires moving from `a123` to `crypto.randomUUID()`)
- `tenant_id`: `uuid` (required for RLS)
- `patient_id`: `uuid` (FK to `patients(tenant_id, id)`)
- `doctor_id`: `uuid` (FK to `doctors(tenant_id, id)`)
- `start_time` / `end_time`: `timestamptz` (maps to frontend `start` / `end`)
- **Constraints**: Includes strict checks for `status`, `payment_type`, and `source`.

## 3. Relationship Impact
- **Patient_id**: `PatientRepository` is already migrated. The UI will pass a valid patient UUID, so the `patient_id` FK is safe.
- **Doctor_id**: This is highly problematic. The frontend will pass `d1`, `d2`, etc., which are neither valid UUIDs nor present in the `doctors` Postgres table.
- **Mixed Backend**: `TreatmentPlans` and `DentalCharts` remain local, but they don't depend on appointments. Appointments can safely move to Supabase once doctors are resolved.

## 4. Doctor Dependency Analysis (CRITICAL)
- Doctors are currently loaded via `LocalStorageDoctorRepository` (seeded in `storage.ts` from `demoDoctors`).
- Doctor IDs are strings like `d1`, `d2`.
- The Supabase `appointments` table defines `doctor_id uuid REFERENCES doctors(tenant_id, id)`.
- If we implement `SupabaseAppointmentRepository` now, passing `doctorId: 'd1'` will result in a Postgres error: `invalid input syntax for type uuid: "d1"`.
- If we alter local doctor IDs to UUIDs in `demoDoctors`, inserting an appointment will result in a Foreign Key violation unless those UUIDs are actually seeded into the Supabase `doctors` table first.
- The UI *requires* `doctorId` to place appointments into columns on the Schedule page.
- **Conclusion**: This is a hard blocker. We cannot migrate `AppointmentRepository` until doctors are migrated or properly seeded with UUIDs and a working `DoctorRepository`.

## 5. Tenant/RLS Readiness
- The `TenantContext` provides `activeTenant.tenantId`.
- No-tenant users are correctly blocked from accessing the schedule.
- `appointments` table has RLS policies enforcing `tenant_id` isolation.
- Readiness: **High**.

## 6. Proposed Migration Strategy
*Once the doctor blocker is resolved:*
- Create `SupabaseAppointmentRepository` implementing `IAppointmentRepository`.
- Expose `createAppointmentRepository({ backend, tenantId })` factory.
- Update `useScheduleAppointments` (and any other relevant hooks) to resolve the backend based on `authMode === 'supabase-active' && activeTenant?.tenantId && isSupabaseConfigured`.
- Leave Dev mode fully on `LocalStorageAppointmentRepository`.

## 7. Query Design
- `listAppointments()`: `supabase.from('appointments').select('*').eq('tenant_id', tenantId)`
- `listAppointmentsByPatient(patientId)`: `supabase.from('appointments').select('*').eq('tenant_id', tenantId).eq('patient_id', patientId).order('start_time', { ascending: false })`
- `createAppointment`: `insert({ ..., tenant_id: tenantId, start_time: appt.start, end_time: appt.end })`
- `updateAppointment`: `update({ ... }).eq('tenant_id', tenantId).eq('id', appt.id)`
- `deleteAppointment`: `delete().eq('tenant_id', tenantId).eq('id', appt.id)`

## 8. ID Strategy
- Update all UI components that create appointments to use `crypto.randomUUID()`. This guarantees compatibility with both Supabase (`uuid` column) and `localStorage`.

## 9. Mixed Backend Risk
- A user logging into the Supabase environment on a new machine will see their Patients and Appointments, but Treatment Plans and Dental Charts will be completely empty. This is expected and acceptable for this phase.

## 10. Tests Required
- Mock tests for factory routing in `useScheduleAppointments.test.tsx`.
- DB mapping tests in `AppointmentRepository.test.ts` (especially checking that `start` maps to `start_time`).
- Verify Dev fallback remains isolated.

## 11. Browser QA Plan
- Verify schedule loads correctly with real tenant_id.
- Create an appointment and verify it appears in the Supabase table with correct timezone handling.
- Verify dragging/resizing appointments updates the row in DB.
- Blocked slots QA (ensure `patient_id` is safely null).

## 12. Risks and Blockers
- **BLOCKER**: `doctor_id` Foreign Key constraint and UUID mismatch.
- **Risk**: Timezone issues when converting between UI ISO strings and Postgres `timestamptz`.

## Final Verdict
- **NOT READY** for AppointmentRepository implementation
- **NOT READY** for TreatmentPlansRepository migration
- **NOT READY** for DentalChartRepository migration
