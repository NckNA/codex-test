# Правила работы ИИ (AI Workflow)

Перед выполнением каждой задачи ИИ **ОБЯЗАН** прочитать следующие файлы:
1. `_ai_work/PRODUCT_CONTEXT.md`
2. `_ai_work/ARCHITECTURE_CURRENT.md`
3. `_ai_work/PROJECT_ROUTES.md`
4. `_ai_work/MEDICAL_DOMAIN_RULES.md`
5. `_ai_work/STORAGE_RULES.md`
6. `_ai_work/CURRENT_TASK.md` (или соответствующий файл в `_ai_work/TASKS/`)

## Основные правила выполнения задач:
- **Выбирать нужный маршрут перед правками**: Понять, в каком контексте находится текущая задача, опираясь на `PROJECT_ROUTES.md`.
- **Не изучать весь проект без необходимости**: Сфокусироваться только на тех файлах, которые напрямую относятся к задаче.
- **Не выходить за маршрут без объяснения**: ИИ не должен трогать глобальные файлы (`main.tsx`, `Layout.tsx`, `storage.ts`), если это не заявлено в задаче. Если нужно, следует явно запросить подтверждение пользователя.
- **Не делать большой рефакторинг без отдельного задания**: Фокус должен быть только на выполнении заявленных критериев (Acceptance criteria).
- **Не менять чужие модули "попутно"**: Избегать исправлений стилей/логики в компонентах, которые случайно попались на глаза, но работают исправно.
- **Не менять storage без явного указания**: Структура хранения критична. Ее нельзя ломать или менять без явной задачи.
- **Обновлять PROJECT_ROUTES.md после изменений**: Если ИИ добавляет новые страницы, компоненты или меняет логику зависимости маршрутов, он обязан зафиксировать это в документации.
- **Создавать отчет в _ai_work/REPORTS/**: Каждая выполненная задача должна завершаться созданием детального markdown отчета о том, что было сделано, как это протестировать и какие ограничения есть.

## Обязательный Capability Reconciliation Gate

Перед DESIGN и тем более перед IMPLEMENT любой новой функции ИИ **ОБЯЗАН** доказать, что функция не дублирует уже существующую возможность DentalFlow, не противоречит существующей доменной модели и не является неполной интерпретацией реального стоматологического workflow.

Для каждой затрагиваемой capability обязательны три источника истины:

1. **DentalFlow current state**: текущий код, schema/RPC/repositories/hooks/UI, тесты, frozen-отчеты и уже принятые решения.
2. **MacDent reference state**: только read-only изучение соответствующего workflow, полей, действий, состояний, ролей, документов, связей и пользовательского сценария. MacDent является функциональным/процессным эталоном, но не источником кода или UI для копирования.
3. **Gap decision**: явное решение `REUSE`, `EXTEND`, `HARDEN`, `REPLACE`, `NEW`, `DEFER` или `NOT_REQUIRED` с доказательством причины.

До реализации необходимо обновить `_ai_work/CAPABILITY_PARITY_MATRIX.md` и присвоить каждой затрагиваемой функции один из статусов: `EXISTS_EQUIVALENT`, `EXISTS_BETTER`, `PARTIAL`, `MISSING`, `WRONG_BOUNDARY`, `REFERENCE_ONLY`, `NOT_REQUIRED`, `UNKNOWN`.

Запрещено:

- создавать новую таблицу, RPC, repository, hook, page, component или отдельную модель, пока не проверено, что эквивалента уже нет;
- считать отсутствие UI доказательством отсутствия функции: capability может уже существовать на schema/repository/RPC уровне;
- считать наличие таблицы или метода завершенной функцией: workflow должен быть проверен end-to-end;
- молча опускать поля, статусы, роли, side effects или lifecycle, существование которых подтверждено эталонным workflow; каждое отклонение должно быть явно принято или отложено;
- механически копировать MacDent code, unique text, assets или pixel-perfect UI;
- переносить MacDent архитектурные слабости, если DentalFlow уже имеет более строгую tenant/security/domain модель.

После IMPLEMENT/VERIFY матрица обновляется повторно по фактическому состоянию. PR не считается готовым к merge, пока отчет задачи не содержит раздел **Capability reconciliation** с ответами: что уже было в DentalFlow, что подтверждено в MacDent, что реально добавлено/изменено, что сознательно не реализовано и почему.

Если одна из сторон не изучена или evidence недостаточно, статус должен оставаться `UNKNOWN`, а реализация блокируется до отдельного STUDY/RECON. Исключение допустимо только для чисто внутренней технической задачи, не меняющей пользовательскую или доменную capability, и это исключение должно быть явно записано в отчете.
