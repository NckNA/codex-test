# Dental CRM / PMS open-source candidates

Дата: 2026-06-08
Ветка: `research/dental-crm-open-source-audit`

Цель: быстро проверить, есть ли готовая легальная open-source база для стоматологической CRM, чтобы не писать с нуля всё то, что человечество уже мучительно написало до нас.

> Важно: не использовать «слитый»/пиратский код. Для CRM с пациентами это особенно опасно: персональные данные, медкарты, платежи, юридические риски. Рассматривать только легальные лицензии: MIT, Apache, GPL и т.п.

---

## Кандидат 1: DentalERP

GitHub: https://github.com/abinauv/dental-erp

Предварительно выглядит как самый близкий к нашему веб-направлению вариант.

### Что заявлено
- Next.js
- Prisma
- MySQL
- MIT license
- пациенты
- записи
- планы лечения
- биллинг
- рецепты
- склад
- управление персоналом
- CRM / loyalty

### Плюсы
- Ближе к современному веб-стеку.
- MIT-лицензия обычно удобнее для коммерческой адаптации, чем GPL.
- Может дать готовые схемы: patients, appointments, billing, treatments.

### Минусы / риски
- Заточен под Индию: GST, Razorpay, PhonePe, Paytm и прочая региональная радость.
- Нужно проверять качество кода и реальную запускаемость.
- Вероятно, придётся сильно чистить локальную специфику.

### Команды для первичной проверки
```bash
git clone https://github.com/abinauv/dental-erp.git
cd dental-erp
npm install
npm run dev
```

Если используется pnpm/yarn или есть Docker, смотреть README проекта. Потому что README, как известно, иногда существует отдельно от реальности.

## Кандидат 2: DentalPin

GitHub: https://github.com/martinezsalmeron/dentalpin

Интересен как возможная база архитектуры или источник идей по модулям.

### Что проверить
- frontend/backend структура
- Docker / docker-compose
- модуль пациентов
- модуль расписания
- модуль лечения
- API-first подход
- лицензия
- активность проекта

### Плюсы
- Похоже на полноценный продукт, а не учебный экран «Hello, dentist».
- Может быть полезен для архитектурных решений.

### Минусы / риски
- Нужно руками проверить зрелость проекта.
- Не факт, что проще адаптировать, чем продолжать наш прототип.

### Команды для первичной проверки
```bash
git clone https://github.com/martinezsalmeron/dentalpin.git
cd dentalpin
```

Дальше смотреть README: Docker, backend/frontend setup, env-файлы.

## Кандидат 3: Apexo

GitHub: https://github.com/alselawi/apexo-flutter

Open-source dental practice manager на Flutter.

### Что заявлено
- Flutter
- офлайн-режим
- пациенты
- записи
- фото
- несколько врачей
- пользователи
- синхронизация
- мультиязычность
- бэкапы
- GPL-3.0

### Плюсы
- Больше похож на готовую стоматологическую систему.
- Может быть полезен как функциональный референс.
- Офлайн-режим интересен для клиники.

### Минусы / риски
- Flutter, а наш текущий прототип на React/Vite.
- GPL-3.0 накладывает обязательства при распространении производной работы.
- Для коммерческой CRM надо внимательно читать лицензию.

### Команды для первичной проверки
```bash
git clone https://github.com/alselawi/apexo-flutter.git
cd apexo-flutter
flutter pub get
flutter run
```

## Кандидат 4: DentneD

GitHub: https://github.com/davidegironi/dentned

Старый dental practice management project.

### Что проверить
- .NET Framework / Windows-зависимости
- SQL Server
- функциональные модули
- отчеты / PDF
- расписание
- лечение / счета

### Плюсы
- Может быть богатым по функциональной логике.
- Полезен как референс: какие разделы нужны стоматологии.

### Минусы / риски
- Технологически старый.
- Не выглядит лучшей базой для современного веб-продукта.
- Скорее «посмотреть идеи», чем брать в основу.

## Кандидат 5: Open Dental

Сайт лицензии: https://www.opendental.com/site/license.html
GitHub old repo / source references нужно проверять отдельно.

### Важное замечание
Open Dental исторически был open-source/GPL, но с версии 24.4 лицензия изменилась на proprietary. Старый код может быть доступен, но строить на этом новый коммерческий продукт рискованно без отдельной юридической проверки.

### Вердикт
Использовать как источник идей, но не как базу проекта без строгого лицензионного аудита.

# Рекомендация

## Самый практичный порядок

1. Сначала проверить `DentalERP`.
   - Ближе к веб-стеку.
   - MIT.
   - Потенциально проще адаптировать под нашу CRM.

2. Потом проверить `DentalPin`.
   - Может быть сильнее по архитектуре.
   - Надо понять, насколько живой и запускаемый.

3. `Apexo` использовать как функциональный эталон.
   - Что должно быть в стоматологической системе.
   - Как устроены пациенты, записи, врачи, офлайн-логика.

4. `DentneD` использовать только как старый справочник логики.

## Что не делать

- Не вливать чужой проект целиком в наш `main`.
- Не смешивать GPL-код с нашим коммерческим кодом без понимания последствий.
- Не хранить реальные данные пациентов в тестовых open-source сборках.
- Не подключать непроверенный проект к рабочей базе клиники.

## Как тестировать безопасно

```bash
mkdir dental-crm-research
cd dental-crm-research

# каждый проект в отдельную папку
git clone https://github.com/abinauv/dental-erp.git
git clone https://github.com/martinezsalmeron/dentalpin.git
git clone https://github.com/alselawi/apexo-flutter.git
git clone https://github.com/davidegironi/dentned.git
```

Запускать только локально, на фейковых данных.

# Предварительный вывод

Готовые базы есть. Но лучший путь не «скачать и заменить наш проект», а сделать аудит и вытащить полезное:

- структуру базы;
- модули пациентов;
- расписание;
- планы лечения;
- счета;
- роли пользователей;
- зубную карту, если есть;
- идеи интерфейса.

Наш текущий проект всё равно имеет смысл, потому что он строится под реальную клинику: русскоязычные скрипты, запись, протезирование, бесплатные консультации, локальные бизнес-процессы, будущая интеграция с WhatsApp/Instagram/AmoCRM. Готовые GitHub-проекты этого не знают, потому что, увы, они не экстрасенсы из Павлодарской области.
