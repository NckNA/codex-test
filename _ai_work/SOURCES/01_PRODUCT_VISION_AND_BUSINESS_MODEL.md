# 01_PRODUCT_VISION_AND_BUSINESS_MODEL.md

## Назначение документа

Этот документ описывает продуктовое видение и бизнес-модель DentalFlow CRM.

Документ нужен, чтобы ChatGPT, Jules, Codex и будущие разработчики понимали:

- для кого создаётся система;
- какую проблему она решает;
- кто будет платить за продукт;
- кто будет ежедневно пользоваться продуктом;
- какие модули являются ядром;
- какие функции относятся к будущим этапам;
- почему DentalFlow должна развиваться как SaaS-платформа;
- почему DentalFlow нельзя проектировать как локальную CRM для одной клиники.

Главное правило:

**DentalFlow CRM — это коммерческий SaaS-продукт для стоматологических клиник, а не разовая внутренняя программа для одной организации.**

---

## Продуктовое видение

DentalFlow CRM — это специализированная SaaS CRM-платформа для стоматологических клиник.

Продукт должен помогать клинике управлять:

- пациентами;
- расписанием;
- врачами;
- кабинетами;
- зубной картой;
- жалобами;
- клиническими находками;
- рисками;
- планами лечения;
- документами;
- оплатами;
- финансами;
- складом;
- отчётами;
- коммуникациями;
- интеграциями.

Главная цель продукта — дать стоматологической клинике единую рабочую систему, где медицинская, административная и коммерческая части связаны, но не смешаны в одну неразборчивую кашу.

DentalFlow должна помогать клинике пройти путь от первого обращения пациента до лечения, оплаты, повторного визита и follow-up.

---

## Главная бизнес-цель

DentalFlow CRM создаётся как коммерческий продукт.

Владелец проекта должен иметь возможность:

- использовать систему в своей стоматологии;
- подключать другие стоматологические клиники;
- продавать доступ к системе по подписке;
- управлять тарифами;
- ограничивать функции по тарифам;
- отключать доступ за неоплату;
- восстанавливать доступ после оплаты;
- развивать систему как SaaS-платформу.

DentalFlow не должна проектироваться как одноразовая CRM для одной клиники.

Если архитектура будет строиться только вокруг одной стоматологии, потом её придётся болезненно переписывать для других клиентов. Это называется “мы быстро сделали MVP”, а потом внезапно выяснили, что MVP умеет жить только в одной клетке.

## Целевая аудитория

Основная целевая аудитория:

- частные стоматологические клиники;
- небольшие сети стоматологических клиник;
- клиники, которые ведут пациентов через Instagram, WhatsApp, звонки и amoCRM;
- клиники, которым нужна связка “продажи → запись → лечение → план лечения → документы → оплата”;
- клиники, которые хотят контролировать пациентов, администраторов, врачей, оплату и повторные визиты.

Потенциальные клиенты DentalFlow:

- одиночная стоматологическая клиника;
- клиника с несколькими врачами;
- клиника с несколькими кабинетами;
- клиника с отделом продаж или администраторами;
- сеть стоматологических клиник;
- управляющая компания стоматологий.

Основные пользователи:

- администратор;

- support платформы.

Каждый пользователь должен видеть свой рабочий контекст.

Администратор не должен страдать от медицинской перегрузки.

Врач не должен тонуть в коммерческом мусоре.

Кассир не должен случайно редактировать зубную карту.

Владелец не должен искать отчёты через пять экранов и две человеческие жертвы интерфейсу.

## Основная проблема рынка

Многие стоматологические клиники работают через набор разрозненных инструментов:

- WhatsApp;
- Instagram;
- amoCRM;
- Excel;
- бумажные карты;
- отдельные программы для записи;
- отдельные документы;
- отдельные таблицы оплат;
- устные договорённости;
- память администратора.

Проблема в том, что эти инструменты часто не связаны между собой.

Из-за этого возникают типичные проблемы:

- пациенты теряются;
- заявки не доходят до записи;
- запись не связана с планом лечения;
- план лечения не доводится до оплаты;
- врач не видит коммерческий статус пациента;
- администратор не понимает медицинскую картину;
- руководитель не видит целостную аналитику;
- данные дублируются;
- документы создаются вручную;
- оплаты ведутся отдельно;
- склад живёт отдельно;
- нет единого источника правды.

DentalFlow должна закрыть этот разрыв.

---

## Ключевая ценность DentalFlow

DentalFlow должна соединить стоматологическую медицинскую логику с управлением клиникой.

Ключевая ценность:

- пациент не теряется;
- источник пациента фиксируется;
- запись понятна;
- врач видит зубную карту;
- жалоба фиксируется;
- клинические находки сохраняются;
- риски не теряются;
- план лечения связан с осмотром;
- пациент получает понятный план;
- администратор видит статус согласования;
- кассир видит оплату;
- владелец видит контроль и отчёты;
- amoCRM получает коммерческий статус, а не медицинскую карту.

DentalFlow должна быть местом, где клиника видит полный путь пациента.

---

## Отличие от обычной CRM

Обычная CRM общего назначения работает с:

- лидами;
- сделками;
- задачами;
- звонками;
- сообщениями;
- воронками;
- менеджерами.

DentalFlow должна работать со стоматологической реальностью:

- пациентами;
- зубной картой;
- состоянием зубов;
- жалобами;
- клиническими находками;
- рисками;
- планами лечения;
- врачами;
- кабинетами;
- расписанием;
- медицинскими документами;
- оплатами;
- складом;
- повторными визитами.

amoCRM может быть сильной системой продаж, но она не должна заменять стоматологическую медицинскую CRM.

DentalFlow должна быть специализированной системой для стоматологий.

---

## Роль amoCRM в бизнес-модели

amoCRM должна быть интеграцией, а не ядром DentalFlow.

amoCRM отвечает за:

- лиды;
- сделки;
- коммуникации;
- воронку продаж;
- задачи менеджерам;
- коммерческий follow-up;
- контроль статуса сделки.

DentalFlow отвечает за:

- пациента;
- медицинскую карту;
- расписание;
- зубную карту;
- жалобы;
- находки;
- риски;
- план лечения;
- документы;
- финансы клиники;
- склад;
- отчёты.

Бизнес-идея интеграции:

```text
amoCRM приводит и ведёт лида
→ DentalFlow ведёт пациента, осмотр, лечение и документы
→ DentalFlow возвращает в amoCRM безопасный коммерческий статус
```

amoCRM не должна получать медицинские детали.

---

## Почему amoCRM не является ядром

amoCRM не является стоматологической медицинской системой.

В amoCRM нельзя безопасно хранить:

- зубную карту;
- номера зубов;
- диагнозы;
- clinical findings;
- riskDescription;
- медицинские документы;
- снимки;
- подробные этапы лечения;
- врачебные заметки.

amoCRM может знать, что пациент получил план лечения и сумма плана составляет определённое значение.

Но amoCRM не должна знать, какие зубы лечить, какие риски выявлены и какие медицинские детали врач указал в DentalFlow.

- телефон;
- дату рождения;
- источник обращения;
- статус лида;
- комментарий;
- аллергию, если используется;
- баланс;
- историю записей;
- медицинские данные;
- планы лечения;
- документы;
- оплаты;
- integration metadata.

Пациент принадлежит конкретному tenant.

Пациент не должен быть глобальным для всей платформы.

---

## Расписание

Модуль расписания должен помогать клинике управлять:

- записями;
- врачами;
- кабинетами;
- временем;
- статусами визитов;
- отменами;
- переносами;
- no-show;
- повторными визитами.

Appointment не является фактом лечения.

Appointment не является оплатой.

Appointment не является выполненной услугой.

---

## Зубная карта

Зубная карта является обязательным модулем стоматологической CRM.

Она должна помогать врачу:

- видеть состояние зубов;
- выбирать зуб;
- отмечать состояние;
- фиксировать проблемы;
- видеть риски;
- связывать находки с планом лечения;
- отличать активные проблемы от закрытых.

Без зубной карты DentalFlow будет обычной CRM с медицинским налётом, что примерно как стоматологический кабинет без кресла: вроде что-то можно делать, но все будут подозревать подвох.

---

## Клинические находки

Clinical findings — это то, что врач выявил при осмотре.

Находка не равна жалобе.

Находка не равна диагнозу.

Находка не равна плану лечения.

Находка не равна оказанной услуге.

Система должна позволять врачу фиксировать находки и связывать их с планом лечения.

---

## Планы лечения

План лечения — один из главных коммерческо-медицинских элементов DentalFlow.

Он должен помогать:

- объяснить пациенту выявленные проблемы;
- показать этапы лечения;
- рассчитать сумму;
- согласовать лечение;
- подготовить документ;
- вернуть коммерческий статус в amoCRM.

План лечения не является фактом выполненной услуги.

Оплата не означает автоматическое выполнение лечения.

Запись не означает автоматическое выполнение лечения.

---

## Документы

DentalFlow должна поддерживать документы.

Будущие документы:

- план лечения;
- информированное согласие;
- договор;
- акт;
- рекомендации;
- выписка;
- направление;
- финансовая выписка.

Документы должны строиться на snapshot.

Документ не должен молча меняться после изменения плана лечения.

---

## Финансы клиники

Финансы клиники должны быть отдельным модулем.

Он может включать:

- оплаты пациентов;
- долги;
- возвраты;
- кассу;
- стоимость планов лечения;
- финансовые отчёты.

Clinic finance нельзя смешивать с platform billing.

Оплата пациента за лечение не является оплатой подписки DentalFlow.

Оплата подписки DentalFlow не является оплатой лечения пациента.

---

## Склад

Склад — будущий модуль.

Он может включать:

- материалы;
- остатки;
- закупки;
- списания;
- движения;
- привязку материалов к выполненным услугам.

Списание материалов должно быть связано с фактом оказанной услуги или отдельным складским действием.

План лечения не должен автоматически списывать склад.

Appointment не должен автоматически списывать склад.

---

## Отчёты

Отчёты нужны владельцу и управляющему клиники.

Будущие отчёты:

- записи;
- no-show;
- загрузка врачей;
- источники пациентов;
- конверсия консультация → план;
- конверсия план → согласование;
- конверсия план → лечение;
- оплаты;
- долги;
- эффективность администраторов;
- эффективность врачей;
- ошибки amoCRM sync;
- активные планы лечения.

Отчёты должны быть tenant-scoped.

Clinic owner не должен видеть отчёты других клиник.

---

## Интеграции

Интеграции являются важной частью продукта, но не должны ломать ядро.

Будущие интеграции:

- amoCRM;
- WhatsApp;
- SMS;
- email;
- телефония;
- онлайн-запись;
- платёжные системы;
- файловое хранилище;
- государственные или медицинские системы, если когда-нибудь потребуется.

Все интеграции должны быть tenant-scoped.

Secrets и tokens должны храниться только server-side.

## SaaS-модель

DentalFlow должна работать по подписке.

Tenant может иметь:

- тариф;
- статус подписки;
- дату окончания периода;
- ограничения функций;
- доступные модули;
- лимиты;
- billing contact.

Возможные статусы:

```text
trial
active
overdue
suspended
cancelled
```

Отключение tenant за неоплату должно ограничивать доступ, но не удалять данные.

---

## Тарифная модель

Финальная тарифная сетка будет определена позже.

Возможные тарифы:

```text
trial
basic
standard
pro
enterprise
```

Примеры тарифных различий:

- количество пользователей;
- количество врачей;
- количество филиалов;
- доступ к amoCRM-интеграции;
- доступ к документам;
- доступ к PDF;
- доступ к складу;
- доступ к расширенным отчётам;
- доступ к multi-branch;
- уровень поддержки.

Тарифы должны управляться платформой.

Backend должен контролировать доступ к функциям, а не только frontend.

---

## Почему нужен billing

Billing нужен не ради красивого экрана оплаты.

Billing нужен, чтобы владелец платформы мог:

- подключать клиники;
- давать trial;
- переводить на тариф;
- видеть просрочку;
- ограничивать доступ;
- отключать tenant;
- восстанавливать доступ;
- контролировать коммерческую модель SaaS.

Без billing DentalFlow будет не SaaS, а программа, которую можно кому-то поставить и потом надеяться, что все честно заплатят. Люди, конечно, существа светлые, но бизнес лучше строить не на наивности.

---

## Почему нужен backend

Production DentalFlow не может быть только frontend-приложением.

Backend нужен для:

- auth;
- tenant isolation;
- roles;
- permissions;
- billing;
- database;
- audit logs;
- documents;
- file storage;
- integrations;
- token storage;
- sync logs;
- security checks;
- backup;
- API.

Frontend может быть удобным интерфейсом.

Backend должен быть защитным и бизнес-слоем.

---

## Почему localStorage временный

localStorage допустим только для раннего прототипа.

localStorage не подходит для production, потому что:

- данные живут в браузере;
- данные можно удалить очисткой кеша;
- нет нормального backup;
- нет настоящего tenant isolation;
- нет централизованного access control;
- нет audit log;
- нельзя безопасно хранить medical data;
- нельзя безопасно хранить financial data;
- нельзя безопасно хранить tokens.

Production source of truth должен быть backend/database.

## Базовая бизнес-модель

Базовая модель:

```text
DentalFlow продаёт доступ клиникам по подписке.
Каждая клиника является tenant.
Клиника платит за доступ к системе.
Платформа управляет тарифами, доступом и ограничениями.
Данные клиники остаются её данными.
При неоплате доступ ограничивается, но данные не удаляются.
```

Это ключевая коммерческая модель проекта.

## Возможные источники дохода

Основной источник дохода:

- ежемесячная или годовая подписка клиники.

Дополнительные будущие источники:

- расширенные тарифы;
- оплата за дополнительные филиалы;
- оплата за дополнительных пользователей;
- платные интеграции;
- платные документы/PDF;
- платные отчёты;
- priority support;
- кастомная настройка;
- внедрение;
- обучение;
- индивидуальные доработки;
- white-label версия.

Не все источники нужны сразу.

Но архитектура не должна закрывать путь к ним.

---

## Что входит в MVP продукта

MVP DentalFlow должен доказать, что стоматологическая клиника может вести ключевой путь пациента в системе.

Минимальный MVP:

- список пациентов;
- карточка пациента;
- базовая зубная карта;
- clinical findings;
- план лечения;
- patient preview;
- базовое расписание;
- источник пациента;
- lead status;
- подготовка amoCRM-интеграции;
- базовый backend/proxy skeleton;
- документационная база проекта.

MVP не обязан сразу быть production SaaS.

Но MVP должен быть построен так, чтобы его можно было развить в production SaaS.

---

## Что не входит в ранний MVP

В ранний MVP не входят:

- полноценная production auth;
- полноценная production database;
- real amoCRM two-way sync;
- платёжная система для подписок;
- полный billing provider;
- warehouse auto-writeoff;
- AI diagnosis;
- автоматическое назначение лечения;
- production PDF engine;
- public online booking;
- массовые WhatsApp-рассылки;
- patient portal;
- multi-branch production mode.

Эти функции могут быть будущими этапами.

---

## Что нельзя продавать как готовое раньше времени

Нельзя называть production-ready то, что является skeleton или placeholder.

Примеры:

- backend skeleton не равен production backend;
- OAuth skeleton не равен полной amoCRM-интеграции;
- disabled button не равен функции;
- localStorage prototype не равен SaaS storage;
- document preview не равен saved legal document;
- memory token store не равен production token storage.

Это нужно честно фиксировать в reports.

---

## Принцип развития продукта

Продукт должен развиваться по слоям:

```text
доменная модель
→ UI прототип
→ source-документы
→ backend architecture
→ tenant model
→ auth/roles
→ database
→ billing/access
→ migration
→ documents
→ real integrations
→ finance
→ warehouse
→ reports
→ release
```

Нельзя строить самые сложные интеграции раньше фундамента.

---

## Главные продуктовые границы

DentalFlow не должна становиться всем сразу.

DentalFlow не должна быть:

- заменой врача;
- медицинским диагностическим ИИ;
- полноценной бухгалтерией;
- складской системой без связи с клиникой;
- копией amoCRM;
- маркетинговой платформой;
- мессенджером;
- системой видеонаблюдения;
- универсальной CRM для любого бизнеса.

DentalFlow должна быть стоматологической CRM-платформой.

---

## Product boundaries

DentalFlow должна чётко разделять:

```text
medical workflow
administrative workflow
commercial workflow
financial workflow
platform billing
integrations
```

Эти области могут быть связаны, но не должны смешиваться.

Примеры:

- план лечения связан с оплатой, но не является оплатой;
- запись связана с услугой, но не является услугой;
- amoCRM связана с пациентом, но не хранит зубную карту;
- platform billing управляет доступом клиники, но не является кассой клиники.

---

## Критерий успешного продукта

DentalFlow можно считать успешной как продукт, если:

- клиника может вести пациентов в системе;
- врач может работать с зубной картой;
- план лечения создаётся понятно;
- пациенту можно показать понятный preview;
- администратор видит статус пациента;
- владелец видит контроль;
- данные клиник изолированы;
- доступ можно ограничить по подписке;
- интеграции работают безопасно;
- медицинские данные не утекают во внешние sales-системы;
- систему можно продать другой клинике без переписывания ядра.

---

## Риски продукта

Основные продуктовые риски:

- построить систему только под одну клинику;
- смешать данные разных tenant;
- сделать слишком сложный интерфейс;
- сделать слишком медицинскую систему для администраторов;
- сделать слишком коммерческую систему для врачей;
- преждевременно уйти в amoCRM sync;
- забыть про billing;
- забыть про backend;
- оставить production на localStorage;
- отправить medical data в amoCRM;
- перепутать план лечения и выполненную услугу;
- перепутать оплату и лечение;
- не сделать документы snapshot-based;
- не сделать отчёты для владельца.

---

## Главный фокус ближайшего периода

Ближайший фокус:

```text
1. Закрепить source-документы 00–18.
2. Стабилизировать medical MVP.
3. Не ломать текущий прототип.
4. Подготовить SaaS foundation.
5. Подготовить backend/database architecture.
6. Не начинать real amoCRM sync раньше времени.
```

Это скучнее, чем сразу подключить всё ко всему.

Зато проект не превратится в комбайн, который красиво гудит и ничего безопасно не делает.

---

## Что нельзя делать

Нельзя:

- строить DentalFlow только под одну клинику;
- делать систему без tenant isolation;
- считать localStorage production-хранилищем;
- отправлять медицинские данные в amoCRM;
- делать real sync до backend/security foundation;
- смешивать platform billing и clinic finance;
- считать запись фактом лечения;
- считать оплату фактом лечения;
- считать план лечения оказанной услугой;
- автоматически ставить диагноз;
- продавать skeleton как готовую функцию;
- делать feature только во frontend без backend enforcement;
- игнорировать роли и права;
- удалять данные клиники за неоплату;
- делать один большой PR на всё сразу.

---

## Правила для ИИ-задач

Если задача касается продукта или бизнес-модели, ИИ должен проверить:

- помогает ли задача строить SaaS CRM для стоматологий;
- не превращает ли DentalFlow в локальную CRM;
- не смешивает ли medical, finance, billing и integrations;
- не добавляет ли production claims для skeleton;
- не делает ли real sync раньше foundation;
- не ломает ли tenant isolation;
- не мешает ли будущей подписочной модели;
- не ухудшает ли путь пациента;
- не усложняет ли UI без пользы.

---

## Acceptance для продуктовых задач

Продуктовая задача считается корректной, если:

- цель задачи связана с DentalFlow как SaaS CRM;
- scope ограничен;
- tenant impact понятен;
- storage impact понятен;
- sensitive data impact понятен;
- medical/commercial/finance границы не нарушены;
- amoCRM не получает medical data;
- billing не смешан с clinic finance;
- задача не преждевременна по roadmap;
- report честно пишет, что не реализовано.

## Итог

DentalFlow CRM должна стать SaaS-платформой, которая помогает стоматологическим клиникам управлять пациентами, записью, зубной картой, планами лечения, документами, оплатами, интеграциями и отчётами.

Главная продуктовая цепочка:

```text
lead
→ patient
→ appointment
→ visit
→ complaint
→ examination
→ dental chart
→ finding
→ treatment plan
→ patient preview
→ document
→ approval
→ treatment
→ payment
→ follow-up
```

Главная бизнес-цепочка:

```text
tenant
→ subscription
→ tariff
→ access
→ usage
→ renewal / suspension
```

Главная интеграционная цепочка:

```text
amoCRM lead
→ DentalFlow patient
→ DentalFlow treatment plan
→ safe commercial summary
→ amoCRM deal / follow-up
```

DentalFlow должна быть не просто “ещё одной CRM”, а управляемой стоматологической SaaS-платформой.

Если держать фокус, продукт можно будет продавать другим клиникам.

Если фокус потерять, получится система, где есть всё понемногу, но ничего нельзя безопасно использовать. А это, увы, уже не инновация, а стандартный результат разработки без границ.
