# 00_PROJECT_MASTER_CONTEXT.md

## Назначение документа
Этот документ является главным контекстом проекта DentalFlow CRM.
Он фиксирует, что именно создаётся, для кого создаётся система, какие архитектурные границы обязательны и какие решения нельзя нарушать в будущих задачах.
Документ должен использоваться ChatGPT, Jules, Codex и другими разработчиками как верхний источник смысла проекта.

Главное правило:
**DentalFlow CRM — это SaaS-платформа для стоматологических клиник, а не локальный frontend-прототип для одной организации.**

Если это забыть, проект быстро превратится в милую демо-CRM, которая красиво открывается в браузере, но разваливается при первой попытке продать её второй клинике. Интернет уже переполнен такими памятниками человеческому оптимизму.

---

## Главный контекст проекта
DentalFlow CRM — это специализированная SaaS CRM-платформа для стоматологических клиник.

Система создаётся не только для внутреннего использования одной стоматологией, а как продукт, который владелец платформы сможет:
- использовать в своей стоматологической клинике;
- подключать другим стоматологическим клиникам;
- продавать по подписке;
- развивать как коммерческий SaaS;
- отключать или ограничивать доступ клиники при неоплате;
- масштабировать на несколько независимых организаций.

DentalFlow должна проектироваться сразу с учётом будущего multi-tenant режима.

NckNA/codex-test

Важно:

## Название проекта
Рабочее название продукта:
```text
DentalFlow CRM
```

Смысл названия:
- Dental — стоматология;
- Flow — поток работы клиники от обращения до лечения, оплаты и повторного визита;
- CRM — система управления пациентами, коммуникацией, записью, планами лечения и бизнес-процессами клиники.

Название может измениться в будущем, но доменная суть проекта должна сохраняться.

---

## Тип продукта
DentalFlow CRM — это:
```text
SaaS CRM platform for dental clinics
```

Проект не является:
- обычной CRM общего назначения;
- копией amoCRM;
- медицинским ИИ-диагностом;
- системой автоматической постановки диагнозов;
- бухгалтерской системой;
- складской системой отдельно от клиники;
- локальным приложением для одной стоматологии;
- игрой;
- учебным sandbox-проектом без бизнес-цели.

DentalFlow может иметь модули финансов, склада, документов и интеграций, но ядром остаётся стоматологическая CRM.

---

## Главная бизнес-идея
Владелец платформы должен иметь возможность подключать стоматологические клиники как отдельных клиентов.
Каждая клиника должна иметь:
- свой доступ;
- своих пользователей;
- своих пациентов;
- своё расписание;
- своих врачей;
- свою зубную карту пациентов;
- свои планы лечения;
- свои документы;
- свои финансы;
- свои интеграции;
- свои настройки;
- свой статус подписки.

Данные клиник не должны перемешиваться.

## Главная техническая идея
DentalFlow должна постепенно перейти от frontend/localStorage-прототипа к production SaaS-архитектуре:
```text
Frontend → Backend API → Database → Tenant isolation → Roles and permissions → Billing and access control → Integrations → Audit logs → Backup / restore
```

На раннем этапе допустим прототип на localStorage. Но production DentalFlow не может хранить основные медицинские и финансовые данные только в браузере пользователя. localStorage — временный инструмент разработки, а не фундамент бизнеса.

Да, это снова скучная правда, которая почему-то спасает проекты от самоуничтожения.

На текущем этапе проект может включать:
- React;

Текущий backend skeleton ещё не является полноценным production backend.
Текущий frontend-прототип ещё не является production SaaS.

## Главная продуктовая цель
DentalFlow должна помочь стоматологической клинике управлять полным рабочим циклом пациента:
```text
обращение → лид → запись → визит → жалоба → осмотр → зубная карта → клинические находки → план лечения → patient preview → документы → согласование → лечение → оплата → повторный визит → follow-up
```

Не каждый пациент проходит весь путь. Но система должна быть готова поддерживать этот путь без смешивания медицинских, административных и коммерческих данных.

---

## Главные пользователи внутри клиники
DentalFlow должна учитывать разные роли внутри стоматологической клиники:
- владелец клиники;
- управляющий;
- администратор;
- регистратор;
- врач-стоматолог;
- ортопед;
- ортодонт;
- хирург;
- кассир;
- складской сотрудник;
- маркетолог;
- руководитель отдела продаж.

Каждая роль должна видеть и делать только то, что ей разрешено. Frontend может скрывать кнопки, но настоящая защита должна быть на backend.

---

## Главные роли платформы
Кроме ролей клиники, в будущем должны быть роли уровня SaaS-платформы:
- platform_owner;
- platform_admin;
- support;
- technical_admin.

Эти роли управляют не лечением пациентов, а самой платформой:
- подключение клиник;
- отключение клиник;
- подписки;
- тарифы;
- техническая поддержка;
- доступы;
- аудит;
- настройки платформы.

Роли платформы нельзя смешивать с ролями клиники. Platform owner не должен автоматически становиться врачом каждой клиники.

---

## Tenant как основа архитектуры
В DentalFlow каждая клиника или компания должна быть отдельным tenant.
В документах используется термин:
```text
tenant
```

Возможные будущие аналоги:
```text
organization
clinic
company
```

Пока не выбрано финальное имя сущности, все архитектурные документы используют `tenantId`.

Главное правило:
**все данные конкретной клиники должны быть tenant-scoped.**

---

## Tenant isolation
Tenant isolation означает:
- клиника A не видит пациентов клиники B;
- клиника A не видит расписание клиники B;
- клиника A не видит документы клиники B;
- клиника A не видит финансы клиники B;
- клиника A не использует amoCRM-токены клиники B;
- клиника A не видит sync logs клиники B;
- пользователь одной клиники не получает доступ к другой клинике без явного membership.

Это правило является обязательным для production-версии.

---

## Billing и отключение доступа
DentalFlow должна поддерживать подписочную модель. Клиника может иметь статус:
```text
trial
active
overdue
suspended
cancelled
```

Владелец платформы должен иметь возможность:
- дать клинике trial;
- активировать подписку;
- изменить тариф;
- ограничить доступ;
- отключить доступ за неоплату;
- восстановить доступ после оплаты.

Главное правило:
**неоплата блокирует или ограничивает доступ, но не удаляет данные клиники.**
Удалять пациентов, документы, планы лечения или медицинскую историю из-за неоплаты запрещено.

---

## Platform billing не равен clinic finance
В системе нужно строго разделять:
```text
Platform Billing
```
и
```text
Clinic Finance
```

Platform Billing — это отношения между DentalFlow и клиникой:
- подписка;
- тариф;
- счёт за SaaS;
- доступ к платформе;
- задолженность клиники перед платформой.

Clinic Finance — это отношения между клиникой и пациентом:
- оплата лечения;
- долг пациента;
- касса;
- возврат пациенту;
- стоимость плана лечения.

Эти области нельзя смешивать.

---

## Медицинская модель
DentalFlow должна уважать стоматологическую медицинскую модель.
Главное разделение:
```text
жалоба пациента ≠ клиническая находка ≠ диагноз ≠ план лечения ≠ оказанная услуга ≠ оплата
```

Система может помогать врачу структурировать данные, но не должна автоматически ставить диагнозы и принимать медицинские решения вместо врача. Врач остаётся ответственным за медицинскую часть.

---

## Зубная карта
Зубная карта — обязательный ключевой модуль DentalFlow.
Она должна позволять:
- видеть состояние зубов;
- выбирать зуб;
- фиксировать состояние зуба;
- создавать clinical findings;
- видеть риски;
- связывать находки с планом лечения;
- отличать активные проблемы от завершённых;
- не смешивать tooth state и finding.

Без зубной карты DentalFlow будет неполноценной стоматологической CRM.

---

## План лечения
План лечения — это предложение или намерение лечения.
План лечения не является фактом оказанной услуги.
Правильная логика:
```text
DentalFinding → TreatmentPlan → TreatmentStage → PatientPreview → MedicalDocument → CompletedService → Payment
```

План лечения может быть согласован пациентом, но это ещё не значит, что лечение выполнено.
Оплата также не должна автоматически означать выполнение лечения.

---

## Документы
Документы должны фиксировать данные на момент создания. Если план лечения изменился после формирования документа, старый документ не должен молча переписываться.

Правильный подход:
```text
Document snapshot
```

Документ для пациента не должен показывать:
- внутренние ID;
- syncStatus;
- amoCRM fields;
- токены;
- raw API errors;
- служебные комментарии;
- технические поля.

---

## Расписание
Appointment — это запись пациента на приём.

Запись не равна:
- факту лечения;
- оказанной услуге;
- оплате;
- завершённому этапу лечения;
- списанию материалов.

Завершение записи в расписании не должно автоматически закрывать medical findings, менять tooth state или создавать payment.

---

## amoCRM
amoCRM является внешней sales/CRM-системой.
amoCRM должна использоваться для:
- лидов;
- сделок;
- коммуникаций;
- follow-up;
- коммерческого статуса;
- задач менеджеру.

amoCRM не является медицинской картой. В amoCRM нельзя отправлять:
- зубную карту;
- номера зубов;
- clinical findings;
- diagnosis;
- riskDescription;
- медицинские документы;
- подробные этапы лечения;
- врачебные заметки;
- PDF с медицинскими деталями.

DentalFlow может передавать в amoCRM только безопасную коммерческо-административную сводку.

---

## amoCRM техническая граница
Frontend не должен обращаться к amoCRM API напрямую.
Правильная схема:
```text
DentalFlow Frontend → DentalFlow Backend / Integration Proxy → amoCRM API
```

Токены amoCRM должны храниться только server-side.
Запрещено хранить во frontend:
- access token;
- refresh token;
- client secret;
- authorization code;
- raw token response.

Запрещено хранить токены в localStorage.

---

## Backend как будущий центр системы
Production DentalFlow должен иметь backend как центральный слой.
Backend отвечает за:
- auth;
- users;
- tenant context;
- roles;
- permissions;
- subscription status;
- billing access;
- validation;
- database access;
- audit logs;
- integration logs;
- documents;
- files;
- external API calls;
- protection of secrets.

Frontend не должен быть единственным слоем безопасности.

---

## Storage strategy
На раннем этапе localStorage допустим для прототипа.
Но production storage должен быть backend/database.

Целевая схема:
```text
localStorage prototype → documented storage model → backend API → tenant-aware database → migrations → audit logs → backup / restore
```

Запрещено:
- считать localStorage production-хранилищем;
- хранить tokens в localStorage;
- делать `localStorage.clear()` как миграцию;
- удалять старые данные без backup;
- ломать старые demo data без migration report.

---

## UI/UX принцип
DentalFlow UI должен быть рабочим инструментом клиники.

Главный UX-принцип:
```text
пользователь должен быстро понять: где он находится, с кем работает, что сейчас важно, что можно сделать, что делать нельзя, что уже сохранено, что требует внимания.
```

UI должен учитывать роли. Врач, администратор, кассир, владелец клиники и platform owner не должны видеть один и тот же интерфейс, если их задачи разные.

## AI workflow
Проект разрабатывается с участием ИИ-агентов:
- ChatGPT;
- Jules;
- Codex;
- будущие агенты или разработчики.

Правильное разделение:
```text
ChatGPT → архитектура, задачи, review, контроль scope
Jules → реализация, branch, commit, push, PR
Codex → проверка, диагностика, аварийная помощь
```

Jules должен сам создавать branch, push и PR.
Codex не должен тратиться на рутинную доставку, если Jules работает нормально.

---

## Правила задач для ИИ-агентов
Каждая задача должна иметь:
- Task ID;
- Title;
- Phase;
- Type;
- Goal;
- Context;
- Relevant sources;
- Scope;
- Allowed files;
- Forbidden files;
- Tenant impact;
- Storage impact;
- Sensitive data impact;
- Acceptance criteria;
- Checks;
- Report requirements;
- Branch name;
- PR title.

Задачи должны быть маленькими, проверяемыми и ограниченными. Один PR — одна идея.

---

## Pull Request как обязательная доставка
Задача не считается завершённой, если:
- branch не запушена;
- PR не создан;
- PR не виден на GitHub;
- commit hash не указан;
- changed files не понятны;
- report отсутствует, если требовался.

Фраза “готово локально” не является доставкой. Это просто сообщение из параллельной вселенной, где код вроде существует, но проекту от этого не легче.

## Roadmap-логика
Разработка должна идти поэтапно:
```text
sources → stable prototype → SaaS architecture → backend/database → auth/tenant/roles → billing/access → migration → documents → real integrations → finance/warehouse/reports → commercial SaaS release
```

Нельзя прыгать сразу в real amoCRM sync без tenant/backend/security foundation.
Нельзя делать production billing без backend enforcement.
Нельзя делать production storage на localStorage.

## Ближайший стратегический приоритет
После создания source-документов нужно:
1. Зафиксировать все источники в `_ai_work/SOURCES/`.
2. Обновить SOURCES_INDEX.md.
3. Закрепить task template и PR review checklist.
4. Стабилизировать medical MVP.
5. Подготовить SaaS foundation.
6. Подготовить backend/database architecture.
7. Только потом возвращаться к real amoCRM sync.

amoCRM skeleton и OAuth skeleton допустимы раньше как подготовительные задачи. Полная real sync должна ждать нормальной tenant/backend/security базы.

## Что нельзя делать
Нельзя:
- проектировать DentalFlow как систему только для одной клиники;
- смешивать данные разных клиник;
- хранить production medical data только в localStorage;
- хранить tokens во frontend;
- обращаться к amoCRM API напрямую из React;
- отправлять medical data в amoCRM;
- смешивать platform billing и clinic finance;
- считать appointment фактом лечения;
- считать payment фактом лечения;
- считать treatment plan оказанной услугой;
- автоматически ставить диагноз;
- переписывать документы задним числом;
- удалять данные tenant за неоплату;
- делать frontend единственным security layer;
- делать большой refactor без отдельной задачи;
- пушить напрямую в main;
- принимать “готово” без PR.

## Главная проверка для любой задачи
Перед любой задачей нужно спросить:
```text
Эта задача помогает строить DentalFlow как SaaS CRM для стоматологических клиник?
```

Если нет — задача либо не нужна, либо преждевременна, либо относится к другому проекту.

Второй вопрос:
```text
Она не ломает tenant isolation, medical safety, storage safety и integration safety?
```

Если ломает — задачу нельзя принимать.

## Итог
DentalFlow CRM должна развиваться как коммерческая SaaS-платформа для стоматологических клиник.

Главная архитектурная цепочка:
```text
Tenant → Users / Roles / Permissions → Patients → Appointments → Dental Chart → Findings → Treatment Plans → Documents → Completed Services → Payments → Reports → Integrations → Billing / Access Control
```

Главная продуктовая цепочка:
```text
lead → patient → appointment → visit → complaint → examination → finding → treatment plan → patient preview → document → approval → treatment → payment → follow-up
```

Главная защитная цепочка:
```text
auth → tenant check → permission check → subscription check → entity ownership check → safe response → audit log
```

DentalFlow должна быть системой, где стоматология, продажи, документы, финансы и интеграции связаны, но не превращены в одну неразборчивую кашу. Если держать эти границы, проект можно развить в продаваемый SaaS. Если не держать, получится очередная CRM, где всё вроде есть, но пользоваться страшно, продавать стыдно, а чинить поздно.
